# ADR-0010: API keys stored as a keyed hash, passwords as argon2id
Status: Proposed (2026-09-27) | Supersedes: none

## Context
Tumnis stores two kinds of secret that it must verify: the human's password (SEC-1) and API keys used by Hermes profiles and scripts (SEC-2). API keys are checked on every request, including agent traffic, and must support prefix lookup, optional expiry, rotation and last-use tracking. Passwords are low-entropy and chosen by a person; API keys are long random secrets generated by the server.

## Options considered
- **argon2id for passwords, HMAC-SHA256 with a server pepper for API keys.** argon2id's memory-hard cost protects low-entropy passwords; a keyed hash is fast for high-entropy keys and useless to an attacker who has the database but not the pepper. Deal-breaker only if the pepper is lost.
- **argon2id for API keys too.** One scheme. Deal-breaker: slow on every request with no gain for random secrets.
- **Plain SHA-256 for API keys.** Fast. Deal-breaker: a database leak alone is enough to test guessed keys offline, with no second secret.

## Decision
Passwords are stored as argon2id hashes (argon2-cffi). API keys have the form `tmn_<prefix>_<secret>`: the prefix is stored in clear for lookup, the secret as HMAC-SHA256 under a server pepper read from `API_KEY_PEPPER_FILE`. Task tokens and device tokens are hashed the same way. Key lookups are cached and dropped through `LISTEN/NOTIFY` on revoke.

## Consequences
- The server pepper must be backed up with the master key; losing it invalidates every API key.
- A revoked key stops working within a second, because every process drops the cached entry on notify.
- Keys are shown once at creation and cannot be recovered, only rotated.
- Status stays Proposed until Scott accepts the security-primitives row in the architecture's Stack and libraries table.
