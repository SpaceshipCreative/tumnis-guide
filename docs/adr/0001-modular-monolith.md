# ADR-0001: Modular monolith on one Postgres, boundaries enforced by import-linter
Status: Accepted (2026-09-27) | Supersedes: none

## Context
Tumnis is built and run by one operator on a homelab (Coolify on Proxmox), with a hosted mode later. PRD design decision 9 asks for a modular monolith: three processes (`api`, `worker`, `daemon`) and one module per subsystem, each owning its tables, router, jobs and tests, talking to the others only through a small public interface and outbox events. Decision 10 asks for Postgres for everything (tables, queue, outbox, full-text search, `LISTEN/NOTIFY`, pgvector), so there is one datastore to back up, fake and reason about. Adding a feature must mean adding a module, registered in one place, and a failing module must lose only its own feature.

## Options considered
- **Modular monolith on one Postgres.** One image, one compose file, one backup stanza; module boundaries are a code rule rather than a network hop. Deal-breaker only if the boundaries are not enforced, because then it decays into a ball of mud.
- **Microservices.** Hard isolation between services. Deal-breaker: many deploys, datastores and failure modes for one operator, with distributed transactions where the outbox now gives atomic state-plus-event commits.
- **Plain monolith without enforced boundaries.** Fastest start. Deal-breaker: nothing stops a module reading another's tables, which is exactly what makes a later split or a per-module kill switch impossible.

## Decision
Tumnis is a modular Python monolith (`backend/tumnis`) with fifteen modules (`auth`, `projects`, `tasks`, `planning`, `agents`, `focus`, `decisions`, `search`, `knowledge`, `integrations`, `calendar`, `github`, `coolify`, `notifications`, `usage`) on a shared `tumnis.core`, all backed by one Postgres 18 cluster with pgvector. Every module has the same shape (`api.py`, `router.py`, `mcp.py`, `models.py`, `rules.py`, `workflows.py`, `events.py`, `adapters/`, `migrations/`, `tests/`) and is registered once in `tumnis/core/modules.py`. Four boundary rules hold: a module imports another only through `tumnis.modules.<name>.api`; no module reads or writes another's tables; `rules.py` imports nothing that does I/O; the module graph has no cycles and `search` and `usage` only subscribe. import-linter contracts in `backend/.importlinter` (modules-api-only, rules-are-pure, core-below-modules, module-graph-acyclic, search-usage-subscribe-only), a Ruff banned-API list and meta-tests enforce them, and the lint job is required in CI.

## Consequences
- One deployable image and one backup (pgBackRest) cover all data, including DBOS state and the outbox.
- Boundaries hold only while the import-linter contracts and the meta-tests in `backend/tests/meta/` stay required in CI; weakening them is a decision that needs a new ADR.
- Module `__init__.py` files stay empty, since a re-export would let `from tumnis.modules.tasks import x` bypass the api-only rule.
- A new module arrives with its tests, fakes, registry entry and import-linter contract (generated by `scripts/new_module.py`), or it does not merge.
- Cross-module reactions go through outbox events (ADR-0011), so they are at least once and every subscriber must be idempotent.
- Tests: T-P0-01-01 to T-P0-01-11 prove the layout, the registry and each boundary contract.
